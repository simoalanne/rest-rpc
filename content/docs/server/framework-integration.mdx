---
title: Framework Integration
description: Register rest-rpc routes on an existing framework such as Hono or Express.
---

rest-rpc has no framework-specific packages. Import from `@rest-rpc/server`
for frameworks built on Fetch `Request`, such as Hono, and from
`@rest-rpc/server/node` for frameworks built on Node's `IncomingMessage`, such
as Express and Fastify. Both export the same functions.

Register each route on the framework's [native router](#native-router) when
the framework should see each route, such as to apply its middleware per route,
or mount all routes under one framework route with the
[catch-all handler](#catch-all-handler).

## Creating Route Handlers

Both ways take the route tree and the
[route options](/docs/server/overview#route-options). `createRouteHandlers`
returns one route per method and path:

```ts
type FetchRoute = {
	method: HttpMethod;
	path: string;
	handle: (request: Request, options?: HandleOptions) => Promise<Response>;
	staticResponse?: Response; // .static() routes: the same object every time
};
```

Routes are ordered with static segments before params, so routers that match
in registration order, such as Express, match `/users/me` before `/users/:id`.

`path` includes any [prefix](/docs/route-builder#path-prefixes) defined with
`.prefix()` and writes params as `:name`, which most routers accept. Rewrite
them for a router that expects another syntax. The Node routes from `@rest-rpc/server/node` have the same shape,
but `handle` takes `req, res` and writes the response to `res`.

## Handle Options

Route handlers and the catch-all handler take per-request options for passing
framework values to rest-rpc:

```ts
type HandleOptions = {
	/**
	 * The initial context the routes require, such as an authenticated user or
	 * the native request. Required when the routes require initial context.
	 */
	context?: TContext;
	/**
	 * Percent-decoded path params, for requests whose URL does not contain the
	 * route path, such as after a rewrite. When omitted, params a router sets,
	 * such as `req.params` in Express, are used, or else they are read from the
	 * request URL. The catch-all handler passes the params it matched.
	 */
	params?: Record<string, string>;
	/**
	 * A request body already parsed by the framework, such as with
	 * `express.json()`. When it is defined, the request body is not read, and the
	 * value is still validated against the route's body schema. Pass the parsed
	 * body whenever a body parser ran, since a route that has to read a body that
	 * was already read rejects instead of responding.
	 */
	body?: unknown;
};
```

See [Values from the Host](/docs/middleware#values-from-the-host) for what
`context` holds.

## Native Router

Register each route's `method` and `path` on the framework's router
and call `route.handle()` from it. The framework does the routing, and
`handle` runs validation, middleware, and the handler.

<Tabs>
<Tab title="Hono">

```ts server.ts
import { Hono } from "hono";
import { createRouteHandlers } from "@rest-rpc/server";
import { routes } from "./routes";

const app = new Hono();

for (const route of createRouteHandlers(routes)) {
	app.on(route.method, route.path, (c) =>
		route.handle(c.req.raw, { context: { user: c.var.user } }),
	);
}
```

</Tab>
<Tab title="Express">

```ts server.ts
import express from "express";
import { createRouteHandlers } from "@rest-rpc/server/node";
import { routes } from "./routes";

const app = express();

for (const route of createRouteHandlers(routes)) {
	const method = route.method.toLowerCase() as
		"get" | "post" | "put" | "patch" | "delete";
	app[method](route.path, (req, res, next) => {
		route.handle(req, res).catch(next);
	});
}
```

</Tab>
</Tabs>

## Catch-All Handler

Pass the route tree to `createCatchAllHandler` and mount it on a single
framework route or middleware. rest-rpc does the routing, using
[rou3](https://github.com/h3js/rou3), and resolves to
`{ matched: true, response }` for the requests it handles, and to
`{ matched: false }` for the rest, so the framework can continue with its own
routes. The Node handler writes the response to `res` and resolves to
`{ matched }`, leaving unmatched requests untouched.

<Tabs>
<Tab title="Hono">

```ts server.ts
import { Hono } from "hono";
import { createCatchAllHandler } from "@rest-rpc/server";
import { routes } from "./routes";

const app = new Hono();
const handler = createCatchAllHandler(routes);

app.all("/api/*", async (c) => {
	const result = await handler(c.req.raw, {
		mountPath: "/api",
		context: { user: c.var.user },
	});
	return result.matched ? result.response : c.notFound();
});
```

</Tab>
<Tab title="Express">

```ts server.ts
import express from "express";
import { createCatchAllHandler } from "@rest-rpc/server/node";
import { routes } from "./routes";

const app = express();
const handler = createCatchAllHandler(routes);

app.use("/api", (req, res, next) => {
	handler(req, res, { mountPath: "/api" }).then(
		({ matched }) => matched || next(),
		next,
	);
});
```

</Tab>
</Tabs>

### Mount Path

When the handler is mounted under a path that is not part of the route paths,
pass it as [`mountPath`](/docs/server/overview#mount-path). It is a
per-request option, so one handler can serve the same routes under several
mount paths. The Node handler reads the path from `req.originalUrl` when the
framework sets it, as Express does when it removes the mount path from
`req.url`, so pass the full mount path.

## Error Handling

[Defined and built-in errors](/docs/http-behavior/errors) are sent as error
responses. Other errors thrown by
handlers or middleware reject the promise returned by `handle` or the
catch-all handler, so pass them to the framework's error handling, as the
Express examples do with `next`.

## Interceptors

Framework middleware only sees error responses, without their `cause`. Both
ways take [`interceptors`](/docs/server/interceptors), which run around each
matched route's `handle`, so `route` is always defined:

```ts
const handlers = createRouteHandlers(routes, {
	interceptors: [onError((error) => logger.error(error))],
});
```

Route errors no interceptor catches are still sent as error responses, and
other errors reject `handle`.
