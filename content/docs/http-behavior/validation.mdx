---
title: Validation
description: What is validated, when, and which type each side sees.
---

Schemas are [Standard Schema](https://standardschema.dev) schemas, such as Zod,
Valibot or ArkType, or `type<T>()` for types without validation. One schema
gives two types, and each side of a route sees one of them:

```ts
const list = route
	.get("/todos")
	.query(z.object({ page: z.coerce.number<number>().int().min(1).default(1) }))
	.response(z.object({ items: z.array(todo), total: z.number() }))
	.handler(({ query }) => listTodos(query.page)); // query.page: number, never undefined

await client.list({ query: {} }); // page is optional for the caller: the schema input
```

| Side                             | Request schemas | Response schemas |
| -------------------------------- | --------------- | ---------------- |
| Client call / handler return     | input           | input            |
| Handler argument / client result | output          | output           |

## Requests

The server validates params, query, headers and body before middleware and the
handler run. A failure is answered with
[`REQUEST_VALIDATION_FAILED`](/docs/http-behavior/errors#built-in-errors) and
status `400`, with the issues of each location as `data`, and the handler
doesn't run. Params, query and headers arrive as
[strings](/docs/http-behavior/encoding#params-query-and-headers), so their
schemas coerce.

A schema that strips unknown keys, such as `z.object()`, passes on only the
keys it declares. One that keeps them, such as `z.looseObject()`, passes on
anything the request sent, `__proto__` included, so don't deep-merge such a
body into another object.

## Responses

A defined response is validated before it's sent, and a stream each item as
it's yielded. A failure is a server bug, so the client gets a bare
`INTERNAL_SERVER_ERROR`, and the issues stay on the server as its `cause`.
Responses inferred from the handler are type-checked but not validated.

## What the Client Receives

The client's result type is the response schema's output, but the body went
through JSON on the way. A value JSON can't represent arrives as what JSON made
of it:

```ts
const getTodo = route
	.get("/todos/:id")
	.response(z.object({ title: z.string(), dueAt: z.date() }))
	.handler(() => ({ title: "Ship", dueAt: new Date() }));

const { body } = await client.getTodo({ params: { id: "1" } });
body.dueAt; // typed Date, but the string "2026-11-17T12:00:00.000Z" at runtime
```

Use schemas whose output is what JSON sends, such as `z.iso.datetime()`, or
restore the value on the client with a `z.coerce.date()` schema and
[`validateResponses`](/docs/client/fetch-client#response-validation).

## Disabling Validation

`disableRequestValidation` and `disableResponseValidation` turn schema
validation off. Everything else still runs, and the types stay as if the
schemas ran:

```ts
const getTodo = route
	.get("/todos/:id")
	.params(z.object({ id: z.coerce.number<number>() }))
	.response(z.object({ title: z.string().default("Untitled") }))
	.handler(({ params }) => findTodo(params.id)); // params.id is the string "1"

createApp(
	{ getTodo },
	{ disableRequestValidation: true, disableResponseValidation: true },
);
```

Coercions, transforms and defaults don't apply, a header default such as a
`content-type` included, and a route with a body accepts any content type.
Disable validation only with schemas that don't change values, or use
`type<T>()` on the routes that need it.

## Types Without Validation

`type<T>()` is a schema that only carries a type. An optional function maps
input to output, and may be async:

```ts
import { type } from "@rest-rpc/server";

const create = route
	.post("/todos")
	.body(type<{ title: string }>()) // accepted as is
	.handler(({ body }) => createTodo(body.title));

const idToString = type((id: number) => String(id)); // input number, output string
```
