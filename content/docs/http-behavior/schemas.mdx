---
title: Schemas and Validation
description: Understand schema input/output types and validation at the HTTP boundary.
---

`rest-rpc` accepts schemas that implement Standard Schema. Zod, Valibot, and
ArkType are supported. The built-in `type<T>()` utility provides types without
runtime validation.

Schemas describe application values. Serialization determines how those values
travel over HTTP. These rules apply to both server runtimes and to both
handler-based routes and separate contracts.

## Schema Input and Output

A schema has an input type and an output type. Validation can coerce, transform,
or add defaults, so the two types can differ.

| Position                               | Type used     |
| -------------------------------------- | ------------- |
| Client request input                   | Schema input  |
| Server handler input                   | Schema output |
| Server handler output or response body | Schema input  |
| Client result or response body         | Schema output |

For inferred handler responses, there is no declared response schema: client
result types come from the handler's return value.

## Request Validation

The server decodes a request, then validates its declared request schemas before
running middleware and the handler. The handler receives validated schema
output. Request validation failures produce a 400 response by default. See
[Error Responses](/docs/http-behavior/errors) for the response body and how to
customize it.

```ts
import { route } from "@rest-rpc/server";
import { z } from "zod";

const list = route
	.get("/todos")
	.query(z.object({ page: z.coerce.number<number>().int().min(1) }))
	.handler(({ query }) => listTodos(query.page));
```

The client accepts a number such as `{ query: { page: 2 } }`. It serializes that
number as an HTTP string. Zod receives `"2"` on the server and coerces it to `2`
for the handler.

## Response Validation on the Server

Declared response schemas validate the handler's response body before
serialization. Declared response headers are validated too. The server sends
the validated schema output.

```ts
const create = route
	.body(z.object({ title: z.string() }))
	.response(z.object({ id: z.string(), title: z.string() }))
	.handler(({ body: { title } }) => ({ id: crypto.randomUUID(), title }));
```

Inferred responses provide type checking without runtime response validation.
Add `.response()` or `.streamResponse()` when runtime validation is needed.
Declared stream schemas validate each item as it is yielded.

Response validation failures produce a generic 500 response by default. See
[Error Responses](/docs/http-behavior/errors).

## Response Validation on the Client

The Fetch client does not validate responses unless `validateResponses` is
enabled. See [Fetch Client](/docs/client/fetch-client#response-validation).

## Disabling Server Validation

`compileRoutes` accepts `disableRequestValidation` and
`disableResponseValidation` options. Both default to `false`. These options
disable only schema validation. Request decoding, content-type checks, route
matching, response status and content-type selection, and response serialization
still run normally.

```ts
compileRoutes(routes, {
	disableRequestValidation: true,
	disableResponseValidation: true,
});
```

The schemas remain part of the route declaration and are still used for type
inference and OpenAPI generation.

:::warning
Do not disable validation if you are using schemas that modify values, such as coercion, transformation, or defaulting.
Those modifications will not be applied to the request segments or response body, which may result in unexpected behavior.

In the example below the `id` parameter will be a string at runtime even though it's typed as a number in the handler.
The `title` property can be missing in the response body because the default value is not applied when response validation is disabled.

```ts
const getTodo = route
	.get("/todos/:id")
	.params(z.object({ id: z.coerce.number<number>().int().min(1) }))
	.response(z.object({ id: z.number(), title: z.string().default("Untitled") }))
	.handler(({ params: { id } }) => {
		const todo: { id: number; title?: string } = getTodoById(id);
		return todo;
	});
```

:::

## Type Utility

When you don't need runtime validation, use the built-in `type<T>()` utility to declare
schemas with only TypeScript types. The utility accepts an optional mapping function
to transform input to output. The mapping function can be asynchronous.

```ts
import { type } from "@rest-rpc/server";

const create = route
	.body(type<{ title: string }>())
	.handler(({ body: { title } }) => ({ id: crypto.randomUUID(), title }));

const numberToStringSchema = type((input: number) => input.toString());
```
