---
title: Serialization and Codecs
description: How values are encoded over HTTP and how to customize body codecs.
---

HTTP values travel through URL strings, headers, or request and response bodies.
These rules are shared by the client and the server. See the
[Route Builder](/docs/route-builder) for declaring the interface and
[Schemas and Validation](/docs/http-behavior/schemas) for validation boundaries.

## Path, Query, and Headers

The client stringifies scalar values. The server passes HTTP strings to request
schemas, which perform any required coercion.

| Location    | Client value shape                                   | Wire representation                                        |
| ----------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| Path params | Object of string, number, or boolean values          | Each value is URL-encoded into its path segment            |
| Query       | Object of scalars, scalar arrays, or optional values | Scalars use `key=value`. Arrays use repeated `key[]=value` |
| Headers     | Object of scalars or optional values                 | String values under lowercase header names                 |

Undefined query and header values are omitted. Missing required path params
fail on the client. Nested query objects are unsupported.

The server reconstructs `tag[]=one&tag[]=two` as `{ tag: ["one", "two"] }`.
A single `tag[]=one` remains an array. Repeated scalar keys such as
`tag=one&tag=two` keep the last value.

Declare header schemas with lowercase names. Incoming header names are
normalized to lowercase, so uppercase schema keys do not match them.

## Bodies and Media Types

Body codecs serialize values into HTTP bodies and deserialize HTTP bodies into
values. Schemas operate on values before encoding and after decoding.

A schema passed to `.body()` or `.response()` declares a JSON body. Other media
types are declared with a record of schemas keyed by base media type, lowercase
and without parameters:

```ts
route
	.post("/todos/import")
	.body({
		"application/json": z.array(z.object({ title: z.string() })),
		"text/csv": z.string(),
	})
	.response({ "text/plain": z.string() });
```

Each media type has its own schema, and requests and responses are unions
discriminated by `contentType`. The client selects the request media type with
[`contentType` in the request](/docs/client/fetch-client#select-a-request-media-type),
and the handler selects the response media type with its returned
`contentType`. Either may be omitted when one media type is declared.

Outgoing codecs are selected from the selected media type. Incoming codecs and
schemas are selected from the received `Content-Type` header. Matching uses the
lowercase base media type without parameters, so
`application/json; charset=utf-8` matches `application/json`.

A request is rejected with `415` before validation when its `Content-Type` is
not declared by the route, or when it has no `Content-Type` and the route
declares several media types. Without a `Content-Type`, a route with one
media type uses it. A client response without a content type or body decodes to
`undefined`.

## Default Codecs

| Content type                                 | Value                                                  |
| -------------------------------------------- | ------------------------------------------------------ |
| `application/json` or any `+json` media type | JSON value                                             |
| `application/x-www-form-urlencoded`          | `URLSearchParams`                                      |
| `multipart/form-data`                        | `FormData`                                             |
| `text/*`                                     | `string`                                               |
| Any other media type                         | `Blob` or `Uint8Array` when sent, `Blob` when received |

The client uses these codecs for requests and responses. The server follows the
same mapping and can also send streams. See
[Request and Response Bodies](/docs/server/fetch#request-and-response-bodies).

## Streams

A `text/event-stream` response is always a server-sent event stream, handled by
rest-rpc on both ends, and custom codecs cannot override it. Its schema
validates each item. The server frames each value a
[streaming route](/docs/streaming) yields as JSON in an SSE `data` field, with
optional `id`, `event`, and `retry` fields, and the client always parses
`text/event-stream` responses as an SSE stream.

## Custom Codecs

Create a codec with `bodyCodec(mediaTypes, operations)` and pass it in
`bodyCodecs` to `compileRoutes` or the client. The same codec works on the
client and on both server runtimes. `mediaTypes` is a media type, a pattern, or
a list of both, and a codec has a `serialize` function, a `deserialize`
function, or both.

A media type string matches one lowercase base media type exactly. A
regular expression matches a family, such as `/\+json$/`. Exact strings take
precedence over patterns, so list a media type exactly to override a default
codec. Patterns are tested in order, custom codecs before the defaults. Each
operation is selected independently, so overriding only serialization keeps the
default deserializer.

<Tabs>
<Tab title="Server">

```ts
import { bodyCodec, compileRoutes } from "@rest-rpc/server";
import { routes } from "./routes";

const binaryCodec = bodyCodec("application/octet-stream", {
	serialize: (value) => {
		if (!(value instanceof Uint8Array)) {
			throw new TypeError("Expected Uint8Array body");
		}
		return value;
	},
	deserialize: async (source) => new Uint8Array(await source.arrayBuffer()),
});

const compiledRoutes = compileRoutes(routes, {
	bodyCodecs: [binaryCodec],
});
```

</Tab>
<Tab title="Client">

```ts
import { bodyCodec, initClient } from "@rest-rpc/core";
import { contract } from "./contract";

const binaryCodec = bodyCodec("application/octet-stream", {
	serialize: (value) => {
		if (!(value instanceof Uint8Array)) {
			throw new TypeError("Expected Uint8Array body");
		}
		return value;
	},
	deserialize: async (source) => new Uint8Array(await source.arrayBuffer()),
});

const client = initClient(contract, {
	baseUrl: "https://api.example.com",
	bodyCodecs: [binaryCodec],
});
```

Use schemas that accept the decoded values, and configure compatible codecs on
both ends.

### Serializer Result

`serialize(value, contentType)` receives the full selected content type,
including parameters, and returns the serialized body:

- A plain body is sent with the
  [previously selected content type](#bodies-and-media-types). On the client it
  must be a Fetch request body. On the server it must be a value the runtime can
  send. See
  [Request and Response Bodies](/docs/server/fetch#request-and-response-bodies).
- `serializedBody(body, headers)` sends a body with its own headers, for codecs
  that set headers such as `content-encoding`. Without a `content-type` header,
  the Fetch `Request` or `Response` sets one for the body, such as
  `multipart/form-data` with its generated boundary for `FormData`. A
  `content-type` header may change parameters but must keep the
  selected base media type, since content types are part of route types.

```ts
import { bodyCodec, serializedBody } from "@rest-rpc/core";

const gzipJsonCodec = bodyCodec("application/json", {
	serialize: (value) =>
		serializedBody(gzip(JSON.stringify(value)), {
			"content-type": "application/json",
			"content-encoding": "gzip",
		}),
});
```

### Deserializer Source

`deserialize(source)` returns the value to validate. `source` is typed as
`Request | Response`: the client passes the Fetch `Response` and the server the
Fetch `Request`. Both share the Fetch body methods, such as `json()` and
`arrayBuffer()`. A codec used only on one side can treat `source` as that type
when it needs an API only one of them has.

On the server, an error thrown while deserializing responds with `400`.
