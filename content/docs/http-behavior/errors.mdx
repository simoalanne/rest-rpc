---
title: Errors
description: How defined and built-in errors are sent, and how other errors reach your framework.
---

Routes return successful responses and throw errors. A route
[defines](/docs/route-builder#define-errors) each error it can respond with
by a unique code, and clients reject with the defined error when they receive
it.

## Wire Format

Every error response rest-rpc sends is JSON with the error's status:

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{ "code": "TODO_NOT_FOUND", "message": "Todo not found", "data": { "id": "42" } }
```

- `code` and `message` are always present, and `data` is present when the error
  has data.
- Defined error headers are sent as response headers.
- `cookies` are sent as `Set-Cookie` headers, one per value.

Any HTTP client can read these responses. The rest-rpc client rejects with a
`RouteError` for each of them, and marks it as defined when the route defines
the code with the received status. See
[Fetch Client](/docs/client/fetch-client#typesafe-error-handling).

## Throwing Errors

Throw `errors.CODE(...)` from a handler or middleware, or throw
`new Definition(...)` for an error defined with `routeError()` from any code.
Both create a `RouteError` and take the same options:

```ts
throw errors.SESSION_EXPIRED({
	data: { userId }, // required when the definition has a `data` schema
	headers: { "x-reason": "expired" }, // required when it has a `headers` schema
	cookies: ["session=; Max-Age=0"], // each sent as its own `Set-Cookie` header
	message: "Sign in again", // overrides the defined message
	cause: error, // never sent
});
```

The route's definition decides the response: its status, and the validated
`data` and headers. When `data` or headers fail validation, an
`INTERNAL_SERVER_ERROR` is sent instead.

An error whose code the route does not define is sent as thrown, with its own
status, `data` and headers, and without validation. Use it for errors that
apply across routes, such as an `UNAUTHORIZED` thrown by auth middleware, and
handle it in a client's general error handling. It is not part of the route's
types, so define the error when clients should handle it per call.

## Built-in Errors

The server sends these errors itself, whether or not a route defines them:

| Code                        | Definition                | Status | `data`                                                 | Sent when                                                                                                                                                                                                       |
| --------------------------- | ------------------------- | ------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `REQUEST_VALIDATION_FAILED` | `RequestValidationFailed` | `400`  | Issues grouped by `body`, `query`, `params`, `headers` | [Request validation](/docs/http-behavior/schemas#request-validation) fails                                                                                                                                      |
| `MALFORMED_REQUEST_BODY`    | `MalformedRequestBody`    | `400`  | none                                                   | The request body cannot be decoded                                                                                                                                                                              |
| `UNSUPPORTED_MEDIA_TYPE`    | `UnsupportedMediaType`    | `415`  | none                                                   | The request `Content-Type` is not defined by a route with a body, or missing when several media types are                                                                                                       |
| `INTERNAL_SERVER_ERROR`     | `InternalServerError`     | `500`  | none                                                   | [Response validation](/docs/http-behavior/schemas#response-validation-on-the-server) fails, including error data, or, with [`createApp`](/docs/server/fetch) only, a handler or middleware throws another error |
| `NOT_FOUND`                 | `NotFound`                | `404`  | none                                                   | No route matches, with `createApp`'s default `notFound` only                                                                                                                                                    |

A route that does not add a built-in error still sends it, and clients
receive it as an untyped `RouteError`. To handle a built-in error with typed
`data`, import its definition from `@rest-rpc/server` and add it to the
route:

```ts
import { RequestValidationFailed, route } from "@rest-rpc/server";

const create = route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.error(RequestValidationFailed)
	.handler(({ body }) => createTodo(body.title));
```

Clients of that route then receive `REQUEST_VALIDATION_FAILED` with its issues
typed as `data`, with the `RequestValidationIssues` type:

```ts
{
	body: ValidationIssue[];
	query: ValidationIssue[];
	params: ValidationIssue[];
	headers: ValidationIssue[];
}
```

An invalid response is a server bug, so clients receive no validation details,
not even that validation failed. For a response validation failure, the
error's `cause` holds the validation `location` and `issues`, and is available
to [`onError`](/docs/server/fetch#error-handling).

A stream item that fails validation cannot change the response status. The
stream ends instead.

## Other Errors

Other errors thrown by handlers, middleware, or custom serializers are not sent
as error responses by compiled routes. They reject the handler promise, and
reach the framework's error handling when routes are registered on a framework.
`createApp` sends them as `INTERNAL_SERVER_ERROR` responses.
