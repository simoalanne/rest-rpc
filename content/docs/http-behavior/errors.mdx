title: Errors
description: What an error response contains, which errors clients can handle typed, and where other errors go.
---

Every error rest-rpc sends is a JSON response with the error's status, whatever
body codecs are configured:

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{ "code": "POST_NOT_FOUND", "message": "Post not found", "data": { "id": "42" } }
```

`data` is present when the error has data, the error's headers are response
headers, and each of its `cookies` is a `Set-Cookie` header. Any HTTP client
can read it, and the rest-rpc client rejects with a `RouteError`.

## Defined and Undefined Errors

A route [defines](/docs/route-builder#define-errors) the errors clients handle
per call. Handlers and middleware throw them with `errors.CODE()`, and other
code with the class `routeError()` creates. Both take the same options:

```ts
throw errors.POST_NOT_FOUND({
	data: { id }, // required when the definition has a `data` schema
	headers: { "x-reason": "deleted" }, // required when it has a `headers` schema
	cookies: ["session=; Max-Age=0"],
	message: "Post was deleted", // replaces the defined message
	cause: error, // never sent
});
```

The definition decides what's sent: its status, and `data` and headers
validated by its schemas. When they fail validation, an `INTERNAL_SERVER_ERROR`
is sent instead.

An error whose code the route doesn't define is sent as thrown. Clients get
an untyped `RouteError`, with `code`, `status` and `data` still readable,
which suits errors that apply across routes:

```ts
throw new RouteError("RATE_LIMITED", { status: 429 });
```

## Built-in Errors

The server sends these itself:

| Code                        | Status | Sent when                                                                                                                             |
| --------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `REQUEST_VALIDATION_FAILED` | `400`  | [Request validation](/docs/http-behavior/validation#requests) fails. `data` has the issues by `body`, `query`, `params` and `headers` |
| `MALFORMED_REQUEST_BODY`    | `400`  | The request body can't be decoded                                                                                                     |
| `UNSUPPORTED_MEDIA_TYPE`    | `415`  | The request [`Content-Type`](/docs/http-behavior/encoding#bodies) isn't one the route accepts                                         |
| `INTERNAL_SERVER_ERROR`     | `500`  | [Response validation](/docs/http-behavior/validation#responses) fails, or, with `createApp`, anything else is thrown                  |
| `NOT_FOUND`                 | `404`  | No route matches, with `createApp`                                                                                                    |

Clients receive them as undefined errors. Add a built-in error's definition to
a route to make its `data` typed:

```ts
import { RequestValidationFailed, route } from "@rest-rpc/server";

const create = route
	.post("/posts")
	.body(z.object({ title: z.string(), body: z.string() }))
	.error(RequestValidationFailed) // data: { body, query, params, headers } issues
	.handler(({ body }) => createPost(body));
```

## Other Errors

Anything else thrown, such as a handler's `Error`, is sent by `createApp` as
an `INTERNAL_SERVER_ERROR`, while
[framework handlers](/docs/server/framework-integration#error-handling) reject
with it for the framework. Its `cause` is never sent.
