---
title: Errors
description: How declared and built-in errors are sent, and how other errors reach your framework.
---

Routes return successful responses and throw errors. A route
[declares](/docs/route-builder#declare-errors) each error it can respond with
by a unique code, and clients reject with the declared error when they receive
it.

## Wire Format

Every error response rest-rpc sends is JSON with the error's status:

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{ "code": "TODO_NOT_FOUND", "message": "Todo not found", "data": { "id": "42" } }
```

- `code` and `message` are always present, and `data` is present when the error
  has data.
- Declared error headers are sent as response headers.

Any HTTP client can read these responses. The rest-rpc client recognizes a code
when the route declares it with the received status, and turns every other
response outside the contract into `UNKNOWN_ERROR`. See
[Fetch Client](/docs/client/fetch-client#handle-errors).

## Throwing Errors

Throw `new errors.CODE(...)` from a handler or middleware, or throw an error
defined with `routeError()` from any code. Both create a `RouteError`.

The route's declaration decides the response: its status, and the validated
`data` and headers. When `data` or headers fail validation, an
`INTERNAL_SERVER_ERROR` is sent instead.

Throwing an error whose code the route does not declare is a programmer error,
so it is not sent. The route rejects with an error that names the route and the
code, as it does for an undeclared response status. It reaches the framework's
error handling, and [`createApp`](/docs/server/fetch) sends it as an
`INTERNAL_SERVER_ERROR`. [Built-in errors](#built-in-errors) are the exception.

## Built-in Errors

The server sends these errors itself, whether or not a route declares them:

| Code                        | Definition                | Status | `data`                                                 | Sent when                                                                                                                                                                                                       |
| --------------------------- | ------------------------- | ------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `REQUEST_VALIDATION_FAILED` | `RequestValidationFailed` | `400`  | Issues grouped by `body`, `query`, `params`, `headers` | [Request validation](/docs/http-behavior/schemas#request-validation) fails                                                                                                                                      |
| `MALFORMED_REQUEST_BODY`    | `MalformedRequestBody`    | `400`  | none                                                   | The request body cannot be decoded                                                                                                                                                                              |
| `UNSUPPORTED_MEDIA_TYPE`    | `UnsupportedMediaType`    | `415`  | none                                                   | The request `Content-Type` is not declared by a route with a body, or missing when several media types are                                                                                                      |
| `INTERNAL_SERVER_ERROR`     | `InternalServerError`     | `500`  | none                                                   | [Response validation](/docs/http-behavior/schemas#response-validation-on-the-server) fails, including error data, or, with [`createApp`](/docs/server/fetch) only, a handler or middleware throws another error |
| `NOT_FOUND`                 | `NotFound`                | `404`  | none                                                   | No route matches, with `createApp`'s default `notFound` only                                                                                                                                                    |

A route that does not declare a built-in error still sends it, but clients do
not know its code and receive it as `UNKNOWN_ERROR`, with the error response
body as `data`. To handle a built-in error by its code, import its definition
from `@rest-rpc/server` and declare it on the route:

```ts
import { RequestValidationFailed, route } from "@rest-rpc/server";

const create = route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.error(RequestValidationFailed)
	.handler(({ body }) => createTodo(body.title));
```

Clients of that route then receive `REQUEST_VALIDATION_FAILED` with its issues
typed as `data`, with the `RequestValidationIssues` type:

```ts
{
	body: ValidationIssue[];
	query: ValidationIssue[];
	params: ValidationIssue[];
	headers: ValidationIssue[];
}
```

Built-in errors differ from errors with other codes a route does not declare:
the server produces built-in errors, so they are always sent, while throwing an
undeclared code is a programmer error that is [never sent](#throwing-errors).

An invalid response is a server bug, so clients receive no validation details,
not even that validation failed. For a response validation failure, the
error's `cause` holds the validation `location` and `issues`, and is available
to [`onError`](/docs/server/fetch#error-handling).

A stream item that fails validation cannot change the response status. The
stream ends instead.

## Other Errors

Other errors thrown by handlers, middleware, or custom serializers are not sent
as error responses by compiled routes. They reject the handler promise, and
reach the framework's error handling when routes are registered on a framework.
`createApp` sends them as `INTERNAL_SERVER_ERROR` responses.
