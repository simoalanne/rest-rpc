---
title: Route Builder
description: Define HTTP routes with request segments, typed responses, and streams.
---

A route builder describes an HTTP interface: a method and path, the request
segments it reads, and the responses it returns.

Schemas can come from Zod, Valibot, ArkType, or another Standard Schema library.
The built-in `type<T>()` utility declares types without runtime validation. See
[Schemas and Validation](/docs/http-behavior/schemas).

## Start with Defaults

```ts
import { route } from "@rest-rpc/server";
import { z } from "zod";

const create = route
	.body(z.object({ title: z.string() }))
	.handler(({ body: { title } }) => ({ id: crypto.randomUUID(), title }));

export const routes = { todos: { create } };
```

Without a method setter, a route uses POST and derives its path from its tree
keys: this route is `POST /todos/create`. A value returned directly from the
handler is the response body with status 200.

Route trees are plain TypeScript objects. Group routes into modules and compose
them where they are registered or used to create a client.

## Choose a Method and Path

```ts
const search = route
	.get("/todos/search")
	.query(z.object({ term: z.string() }))
	.handler(({ query: { term } }) => searchTodos(term));

const todo = route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.handler(({ body: { title } }) => createTodo(title));
```

Use `.get(path)`, `.post(path)`, `.put(path)`, `.patch(path)`, or `.delete(path)`.
A method can be selected once per route.

Paths can contain dynamic segments using either `:id` or `{id}` syntax. Without
a `.params()` schema, each dynamic segment is a string param:

```ts
const getTodo = route
	.get("/todos/:id")
	.handler(({ params }) => findTodo(params.id)); // params: { id: string }
```

Declare `.params()` to validate or transform them. Other router syntax, such as
wildcards or regular expressions, is not officially supported.

The path can also be omitted, in which case the route keeps deriving its path
from its tree keys but uses the specified method instead of the default POST.

```ts
const getRoute = route.get();

const listTodos = getRoute.handler(() => listTodos());
const listNotes = getRoute.handler(() => listNotes());
```

## Declare Request Segments

Use `.params()`, `.query()`, `.headers()`, and `.body()` to read each HTTP
request location.

```ts
const update = route
	.patch("/todos/:id")
	.params(z.object({ id: z.string() }))
	.query(z.object({ notify: z.enum(["yes", "no"]).optional() }))
	.headers(z.object({ "x-request-id": z.string().optional() }))
	.body(z.object({ title: z.string() }))
	.handler(({ params, query, headers, body }) =>
		updateTodo(params.id, body.title, {
			notify: query.notify === "yes",
			requestId: headers["x-request-id"],
		}),
	);
```

The following rules apply to request segments:

- `.params()` schemas replace the inferred string params, so they must cover
  every dynamic path segment. Their keys cannot be optional, and a route that
  declares params must have dynamic segments.
- `.body()` is not available on GET routes, and `.get()` is not available after `.body()`.

Header schemas must use lowercase names. See
[Serialization and Codecs](/docs/http-behavior/serialization#path-query-and-headers)
for how each location is encoded.

## Stacking Schemas

Stacking schemas is supported for `body`, `query`, `params`, and `headers`. Each schema is validated in declaration order
against the original request value. The schema outputs are shallow-merged into a single object.

:::warning
When stacking schemas, the output of each schema must be an object. Non-object outputs will throw a runtime error
during validation. Use single schema validation for non-object outputs. Avoid using strict schemas such as `z.strictObject()`
that forbid unknown keys, if those keys are required by the other schemas in the stack.
:::

```ts
const stacked = route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.body(z.object({ description: z.string().optional() }))
	.handler(({ body }) => createTodo(body.title, body.description));
```

## Return Responses

A handler returns either a response envelope or a body:

- An object with a numeric `status` is a response envelope:
  `{ status, body?, contentType?, headers? }`.
- Any other value is the response body with status 200.

Without declared responses, the returned statuses and body types become the
client's result type:

```ts
const get = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.handler(({ params }) => {
		const todo = findTodo(params.id);
		return todo ?? { status: 404, body: { code: "TODO_NOT_FOUND" as const } };
	});
```

:::note
A body that has a numeric `status` field of its own is read as an envelope.
Return it wrapped, as `{ status: 200, body: value }`.
:::

## Declare Responses

Use `.response(schema, options)` to declare response schemas with runtime
validation. Set a status other than 200 with the `status` option. Each status
can be declared once, and a handler returning a status that is not declared
fails at runtime.

```ts
const get = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(todoSchema)
	.response(z.object({ code: z.literal("TODO_NOT_FOUND") }), { status: 404 })
	.handler(({ params }) => {
		const todo = findTodo(params.id);
		return todo ?? { status: 404, body: { code: "TODO_NOT_FOUND" } };
	});
```

Pass only options for a bodyless response, such as `.response({ status: 204 })`.
Declare status-specific response headers with the `headers` option and return
them as `headers`. The option is available on every response, including
bodyless responses and `.streamResponse()`:

```ts
route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.response(todoSchema, {
		status: 201,
		headers: z.object({ location: z.string() }),
	})
	.handler(({ body }) => {
		const todo = createTodo(body.title);
		return {
			status: 201,
			body: todo,
			headers: { location: `/todos/${todo.id}` },
		};
	});
```

## Declare Media Types

Bodies passed as a schema are JSON. For text, forms, binary values, or several
media types, pass a record of schemas keyed by base media type:

```ts
const report = route
	.get("/todos/report")
	.response({ "text/plain": z.string() })
	.handler(() => createTodoReport());
```

With several media types, requests and responses are unions discriminated by
`contentType`. The handler receives the request media type with a narrowed
`body`, and selects a response media type with its returned `contentType`:

```ts
const importTodos = route
	.post("/todos/import")
	.body({
		"application/json": z.array(z.object({ title: z.string() })),
		"text/csv": z.string(),
	})
	.response({ "application/json": z.object({ count: z.number() }) })
	.handler(({ contentType, body }) => {
		const titles =
			contentType === "text/csv"
				? body.split("\n")
				: body.map((todo) => todo.title);
		return { count: titles.length };
	});
```

`contentType` may be omitted when a status declares one media type. Clients
select the request media type with `contentType` in the
[request](/docs/client/fetch-client#select-a-request-media-type). Repeated
`.body()` calls [stack](#stacking-schemas) schemas per media type, and a schema
passed alone counts as `application/json`.

Without declared responses, return the body in an envelope with its
`contentType`, and the media type is inferred. See
[Serialization and Codecs](/docs/http-behavior/serialization) for decoded value
types and compatible codecs.

## Return Streams

Returning an async iterable infers an SSE stream. Use `.streamResponse()` to
declare its data schema.

```ts
const events = route
	.get("/todos/events")
	.streamResponse(z.object({ id: z.string(), message: z.string() }))
	.handler(() => streamTodoEvents());
```

`.streamResponse(schema)` is sugar for `.response({ "text/event-stream": schema })`,
so it declares the whole status. To offer a stream and another media type on the
same status, declare both in one record and select one with `contentType`:

```ts
const todos = route
	.get("/todos")
	.response({
		"application/json": z.array(todoSchema),
		"text/event-stream": todoSchema,
	})
	.handler(() =>
		wantsStream()
			? { status: 200, contentType: "text/event-stream", body: streamTodos() }
			: { status: 200, contentType: "application/json", body: listTodos() },
	);
```

See [Streaming](/docs/streaming) for handlers, event metadata, validation, and
resuming streams.

## Add Metadata and OpenAPI Details

`.metadata()` attaches application information. `.openAPI()` describes the
operation for OpenAPI generation.

```ts
const list = route
	.get("/todos")
	.metadata({ auth: "required" })
	.openAPI({ summary: "List todos", tags: ["Todos"] })
	.response(z.array(todoSchema))
	.handler(() => listTodos());
```

Both can be called more than once. Metadata objects are shallow-merged, and
OpenAPI details are merged with tags combined. Read metadata from the handler's
`route` argument or middleware. See [OpenAPI](/docs/openapi)
for document generation.

## Reuse Builders

Every builder method returns a new route value, so a partially built route can
be shared as a base for other routes without affecting them:

```ts
const authenticated = route
	.headers(z.object({ authorization: z.string() }))
	.metadata({ auth: "required" });

const list = authenticated.get("/todos").handler(() => listTodos());
const remove = authenticated
	.delete("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response({ status: 204 })
	.handler(({ params }) => {
		deleteTodo(params.id);
		return { status: 204 };
	});
```

A route cannot be changed after `.handler()` is attached.

## Handler Arguments

A handler receives one object containing:

- The validated request: `params`, `query`, `headers`, and `body`.
- `context`: the per-request [context](/docs/context) shared with middleware.
- `route`: the route declaration, including its method, path, and `metadata`.
- `contentType`: the request body media type. Routes with a body narrow it to
  their declared media types, and `body` with it.
- `signal`: an `AbortSignal` that aborts when the client disconnects.

Native request objects are not passed to handlers. To make them or other host
values available, [seed the context](/docs/context#values-from-the-host).

## Type Helpers

Use the type helpers to reuse a route's types in code that lives outside the
route, such as service functions or separately written handlers. For
client-side types, see
[Fetch Client](/docs/client/fetch-client#type-helpers).

Infer from a route declared without `.handler()`, or from a contract route. A
type inferred from a completed route cannot be used inside that route's own
handler, because the route's type depends on the handler.

Each helper also accepts a route tree and infers a matching tree of types.
Declare one type for your routes and index into it where a route's type is
needed:

```ts
import type { InferServerRequest } from "@rest-rpc/server";
import type { routes } from "./routes";

export type ServerRequests = InferServerRequest<typeof routes>;

type CreateTodoRequest = ServerRequests["todos"]["create"];
```

### Infer Server Request

`InferServerRequest` is the validated request a handler receives, without
context or `signal`. Use it to pass validated input to code that does
not depend on the server framework.

```ts twoslash
import type { InferServerRequest } from "@rest-rpc/server";
import { route } from "@rest-rpc/server";
import z from "zod";

const updateDeclaration = route
	.patch("/todos/:id")
	.params(z.object({ id: z.string() }))
	.body(z.object({ title: z.string() }));

type UpdateTodoRequest = InferServerRequest<typeof updateDeclaration>;

const updateTodo = ({ params, body }: UpdateTodoRequest) => ({
	id: params.id,
	title: body.title,
});

const update = updateDeclaration.handler(updateTodo);
```

### Infer Server Response

`InferServerResponse` is the union of response envelopes a handler can return
for the responses declared with `.response()`. When responses are inferred
from the handler, there is no declared response to infer before `.handler()`.

```ts twoslash
import type { InferServerResponse } from "@rest-rpc/server";
import { route } from "@rest-rpc/server";
import z from "zod";

const todoSchema = z.object({ id: z.string(), title: z.string() });

const getDeclaration = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(todoSchema)
	.response(z.object({ code: z.literal("TODO_NOT_FOUND") }), { status: 404 });

type GetTodoResponse = InferServerResponse<typeof getDeclaration>;

const findTodo = (id: string): GetTodoResponse =>
	id === "todo_1"
		? { status: 200, body: { id, title: "Write docs" } }
		: { status: 404, body: { code: "TODO_NOT_FOUND" } };

const get = getDeclaration.handler(({ params }) => findTodo(params.id));
```

### Infer Server Handler

`InferServerHandler` is the full handler signature, including context and
`signal`. Use it to write a handler separately from its declaration:

```ts twoslash
import { route, type InferServerHandler } from "@rest-rpc/server";
import z from "zod";

const todoSchema = z.object({ id: z.string(), title: z.string() });

const getDeclaration = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(todoSchema)
	.response(z.object({ code: z.literal("TODO_NOT_FOUND") }), { status: 404 });

const getTodo: InferServerHandler<typeof getDeclaration> = ({ params }) =>
	params.id === "todo_1"
		? { status: 200, body: { id: params.id, title: "Write docs" } }
		: { status: 404, body: { code: "TODO_NOT_FOUND" } };

const get = getDeclaration.handler(getTodo);
```
