---
title: Middleware
description: Wrap route execution with shared application context.
---

Use `.use()` to implement guards, transactions, cleanup, timing, and caching
around route handlers. Route middleware runs after request validation, so it
receives the same validated request as the handler.

## Add Middleware

`next()` executes the remaining middleware and handler. Return its result to
forward downstream output, or return another value to replace it. Returning
without calling `next()` short-circuits the chain. Call `next()` at most once.

```ts
import { route } from "@rest-rpc/server";

const getProfile = route
	.$context<{ user?: User }>()
	.get("/profile")
	.headers(z.object({ authorization: z.string().optional() }))
	.response(z.object({ user: userSchema }))
	.error("UNAUTHORIZED", { status: 401 })
	.use(async ({ next }) => {
		const started = performance.now();
		try {
			return await next();
		} finally {
			console.log(performance.now() - started);
		}
	})
	.use(async ({ headers, context, errors, next }) => {
		const user = await authenticate(headers.authorization);
		if (!user) throw errors.UNAUTHORIZED();
		context.set("user", user);
		return next();
	})
	.handler(({ context }) => ({
		status: 200,
		body: { user: context.get("user")! },
	}));
```

Middleware runs in declaration order; work after `await next()` runs in reverse
order. Request schemas validate before middleware runs, regardless of setter order.

Middleware receives the same arguments as the handler, including
[context](/docs/context), the request `signal`, and the declared `errors`.
Declare request schemas and errors before `.use()` to receive their types.

## Reuse Middleware

When a middleware function should be applied to multiple routes,
declare it once with `route.middleware()` and pass it to `.use()`.

```ts
const transaction = route.middleware(({ next }) =>
	db.transaction(() => next()),
);
const base = route.use(transaction);

const getTodos = base.get("/todos").handler(() => listTodos());
```

Adding middleware to one builder branch leaves sibling stacks unchanged.

:::tip
If the middleware should only be usable on a route with a specific request shape
or declared errors, pass them as a type argument. The middleware can then only be
used on routes whose request and errors match it.
:::

```ts
const Unauthorized = routeError("UNAUTHORIZED", { status: 401 });

const attachUser = route.$context<{ user?: User }>().middleware<{
	headers: { authorization: string };
	errors: { UNAUTHORIZED: typeof Unauthorized };
}>(async ({ headers, errors, next, context }) => {
	const user = await authenticate(headers.authorization);
	if (!user) throw errors.UNAUTHORIZED();
	context.set("user", user);
	return await next();
});

const authenticated = route
	.$context<{ user?: User }>()
	.headers(z.object({ authorization: z.string() }))
	.error(Unauthorized)
	.use(attachUser);

const getUserProfile = authenticated.get("/profile").handler(({ context }) => ({
	user: getProfileForUser(context.get("user")!.id),
}));
```

Without the type argument, reusable middleware receives `errors` with unknown
values. It can still throw an imported [error definition](/docs/route-builder#define-errors-once),
which routes that use the middleware must declare.

## Outputs and Errors

Middleware receives and returns raw application output. A value returned by
middleware is handled like a handler result: response validation and
serialization run after the chain completes. Middleware return values are not
type checked and do not change the client contract, so declare a
`.response()` for every status your middleware can return.

Downstream errors propagate through `next()`, allowing middleware to catch errors
or clean up in `finally`. Catch errors of your own domain code there to throw
the route's declared errors instead:

```ts
const users = route.error(UserNotFound).use(async ({ next }) => {
	try {
		return await next();
	} catch (error) {
		if (error instanceof RecordNotFound) {
			throw new UserNotFound({ data: { id: error.id }, cause: error });
		}
		throw error;
	}
});
```

Response delivery and stream consumption happen outside this wrapping scope.
