title: Middleware

Use `.use()` to implement guards, transactions, cleanup, timing, and caching
around route handlers. Route middleware runs after request validation, so it
receives the same validated request as the handler. Middleware passes values
to handlers through [context](#context), and reads what each route declares
about itself from its [metadata](#metadata).

For contract-first routes, these are called on the `implement()` result. See
[Contract-first](/docs/contract-first#context-middleware-and-metadata).

## Add Middleware

`next()` runs the remaining middleware and the handler, and resolves to their
response. Middleware returns that response, or a [`respond()`](/docs/route-builder#return-responses)
result to short-circuit the chain without calling `next()`. Returning a value
that is not a response is a type error, and throws at runtime. Call `next()` at
most once.

```ts
import { route } from "@rest-rpc/server";

const getProfile = route
	.$context<{ headers: Headers }>()
	.get("/profile")
	.response(z.object({ user: userSchema }))
	.error("UNAUTHORIZED", { status: 401 })
	.use(async ({ next }) => {
		const started = performance.now();
		try {
			return await next();
		} finally {
			console.log(performance.now() - started);
		}
	})
	.use(async ({ context, errors, next }) => {
		const user = await authenticate(context.headers.get("authorization"));
		if (!user) throw errors.UNAUTHORIZED();
		return next({ context: { user } });
	})
	.handler(({ context }) => ({ user: context.user }));
```

Middleware runs in definition order; work after `await next()` runs in reverse
order. Request schemas validate before middleware runs, regardless of setter order.

Middleware receives the same arguments as the handler, including
[context](#context), the request `signal`, and the defined `errors`.
Define request schemas and errors before `.use()` to receive their types.

## Context

Handlers and middleware receive a readonly `context` object for each request.
It holds two kinds of values:

- Initial context, which the host provides for every request. Declare it with
  `route.$context<T>()`.
- Injected context, which middleware adds with `next({ context })`. It is
  available to all later middleware and the handler.

```ts
const app = route.$context<{ db: Db; headers: Headers }>();

const withSession = app.use(async ({ context, next }) => {
	const user = await findSession(
		context.db,
		context.headers.get("authorization"),
	);
	return next({ context: { user } }); // user: User | undefined
});

const getProfile = withSession
	.get("/profile")
	.handler(({ context }) => context.user);
```

Injected values are typed for everything after the middleware that injects
them, so they never need a non-null assertion. To inject a value only some
requests have, inject it on every path with an optional type, as above.

`$context<T>()` can be called at any point of a route chain. Every declaration
is a requirement of the routes built from it, so repeated declarations of a key
must all be satisfied, starting from the [global context](#global-context).

### Global Context

To declare initial context every route requires, augment `DefaultContext` in
`@rest-rpc/server`:

```ts
declare module "@rest-rpc/server" {
	interface DefaultContext {
		db: Db;
	}
}
```

### Values from the Host

The host provides the initial context of each request, such as a database
client, a user authenticated by framework middleware or the native request.
With `createApp`, pass the values or a function that returns them per request
as its [`context`](/docs/server/fetch#app-options) option:

```ts
createApp(routes, {
	context: async (request) => ({ db, headers: request.headers }),
});
```

When [integrating with a framework](/docs/server/framework-integration), pass them as the
`context` [handle option](/docs/server/framework-integration#handle-options) of the
catch-all handler or a compiled route:

```ts
await handler(request, { context: { db, headers: request.headers } });
```

The option is required, and type checked, when routes declare initial context.
A route tree requires the initial context of all of its routes.

## Metadata

Route metadata is how a route describes itself to code that runs on many
routes, such as reusable middleware and
[OpenAPI transforms](/docs/openapi#transform-hooks). `route.$meta<T>()`
declares the shape of the metadata for routes built from the returned builder.
`.meta()` is available once a shape is declared, and only accepts values of
that shape:

```ts
type Permission = "todos:read" | "todos:write";

const app = route.$meta<{ access: "public" | "signed-in" | Permission }>();

app.get("/health").meta({ access: "public" });
app.post("/todos").meta({ access: "todos:delete" }); // type error
```

Repeated `.meta()` calls are shallow-merged. `$meta<T>()` can be called at any
point of a route chain, and where a key is already in the shape, its type from
`T` is used.

Middleware and handlers read the metadata from `route.meta`. Reusable
middleware and inline middleware added before `.meta()` receive it as
`Partial<T> | undefined`, since the route may set any of its keys or none.
Handlers and inline middleware added after `.meta()` receive the values set on
the route.

### Global Metadata

To use one shape for every route without calling `$meta<T>()`, augment
`DefaultMeta`. It also types `route.meta` in OpenAPI transforms. For routes
defined with `@rest-rpc/core`, augment `@rest-rpc/core` instead.

```ts
declare module "@rest-rpc/server" {
	interface DefaultMeta {
		access: "public" | "signed-in" | Permission;
	}
}
```

## Reuse Middleware

When a middleware function should be applied to multiple routes,
define it once with `route.middleware()` and pass it to `.use()`.

```ts
const transaction = route.middleware(({ next }) =>
	db.transaction(() => next()),
);
const base = route.use(transaction);

const getTodos = base.get("/todos").handler(() => listTodos());
```

Adding middleware to one builder branch leaves sibling stacks unchanged.

Reusable middleware is typed by the builder it is defined on: its request
schemas, errors, context and metadata shape. It can only be used on routes
whose request, errors and metadata match it. Context it reads that the route
does not have yet becomes initial context of the route, which the host provides.

```ts
const Unauthorized = routeError("UNAUTHORIZED", { status: 401 });

const authenticated = route
	.$context<{ db: Db }>()
	.headers(z.object({ authorization: z.string() }))
	.error(Unauthorized);

const attachUser = authenticated.middleware(
	async ({ headers, errors, next, context }) => {
		const user = await authenticate(context.db, headers.authorization);
		if (!user) throw errors.UNAUTHORIZED();
		return next({ context: { user } });
	},
);

// Requires db from the host, and receives user from attachUser.
const getUserProfile = route
	.headers(z.object({ authorization: z.string() }))
	.error(Unauthorized)
	.use(attachUser)
	.get("/profile")
	.handler(({ context }) => ({ user: getProfileForUser(context.user.id) }));
```

:::tip
To require request fields or errors without defining schemas for them, pass
them as a type argument, such as
`route.middleware<{ headers: { authorization: string } }>()`.
:::

Without a defined error or type argument, reusable middleware receives `errors` with unknown
values. It can still throw an imported [error definition](/docs/route-builder#define-errors-once),
which routes that use the middleware must define.

## Responses and Errors

`next()` resolves to the downstream response as a `respond()` envelope, with
its `status`, `body`, `headers` and `contentType`. Response validation and
serialization run once, after the chain completes.

Middleware returns that response, or ends the chain with the `respond` it
receives, which only accepts the statuses defined before the middleware. An
object of the same shape, with any of those fields, is a response too. A
response kept outside the request has the type `MiddlewareResponse`, and
middleware may return it as-is. Responses that middleware creates or changes are validated like the handler's.
Throw [defined errors](/docs/route-builder#define-errors) for failures instead
of returning error responses.

```ts
const listTodos = route
	.get("/todos")
	.response(z.array(todoSchema))
	.response({ status: 204 })
	.use(async ({ respond, next }) =>
		isPaused() ? respond(undefined, { status: 204 }) : next(),
	)
	.handler(() => findTodos());
```

Downstream errors propagate through `next()`, allowing middleware to catch errors
or clean up in `finally`. Catch errors of your own domain code there to throw
the route's defined errors instead:

```ts
const users = route.error(UserNotFound).use(async ({ next }) => {
	try {
		return await next();
	} catch (error) {
		if (error instanceof RecordNotFound) {
			throw new UserNotFound({ data: { id: error.id }, cause: error });
		}
		throw error;
	}
});
```

Response delivery and stream consumption happen outside this wrapping scope.
