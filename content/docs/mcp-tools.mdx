---
title: MCP Tools
description: Expose routes to agents as MCP tools, or as tools of an agent framework.
---

You have an API, and you want agents to use it too. Agents use APIs through
tools: definitions a model reads, with a name, a description and a JSON Schema
of the arguments, and functions that run the calls the model makes.
[MCP](https://modelcontextprotocol.io) is the standard way to serve tools, so
any agent that supports it, such as a chat app or an editor, can connect to
them.

Serving an API over MCP usually means wrapping it by hand: writing a tool for
each endpoint, with its own schema and a handler that calls the API, and
keeping them in sync as the API changes. A rest-rpc route already is that
definition, with a name in the route tree, schemas, and a handler behind
validation and middleware. `createToolsFromRoutes()` turns rest-rpc routes
into tools, so the same routes serve HTTP clients and agents, and each tool
call runs the route as an HTTP request does.

The tools are plain data. Register them with the
[MCP TypeScript SDK](https://ts.sdk.modelcontextprotocol.io), which serves them
and provides sessions, authorization, resources and prompts, or use them in an
agent framework, such as the [AI SDK](https://ai-sdk.dev), that runs agents in
your own process.

:::warning[JSON Only]
Tool arguments and results are JSON. Routes whose definition declares anything else are left out when the tools are created.
When the route doesn't define a response schema, returning a body that isn't JSON fails the call at runtime with an `INTERNAL_SERVER_ERROR`.
:::

## Create Tools

`createToolsFromRoutes()` converts each compatible route into a tool.

```ts router.ts
import { route } from "@rest-rpc/server";
import * as z from "zod";

const post = z.object({ id: z.string(), title: z.string(), body: z.string() });
const posts = [{ id: "1", title: "Hello", body: "First post" }];

export const router = {
	posts: {
		search: route
			.get("/posts/search")
			.query(z.object({ text: z.string().describe("Words to find in posts") }))
			.response(z.object({ posts: z.array(post) }))
			.openAPI({ summary: "Search posts by their title and body" })
			.handler(({ query }) => ({
				posts: posts.filter(({ title, body }) =>
					`${title} ${body}`.includes(query.text),
				),
			})),
	},
};
```

```ts tools.ts
import { createToolsFromRoutes } from "@rest-rpc/server";
import * as z from "zod";
import { router } from "./router.ts";

export const tools = createToolsFromRoutes(router, {
	schemaConverter: (schema, io) => z.toJSONSchema(schema as z.ZodType, { io }),
});
```

## Tool Definitions

Each tool is plain data shaped like an MCP tool of protocol revision 2026-07-28,
with the route it calls:

```ts
type ToolFromRoute = {
	/** The definition the model reads, an MCP `Tool`. */
	definition: {
		/** The key path joined with `_`, such as `posts_search`. */
		name: string;
		/** The `summary` of `.openAPI()`. */
		title?: string;
		/** The `description` of `.openAPI()`, otherwise its `summary`, otherwise the method and path, such as `GET /posts/search`. */
		description?: string;
		/**
		 * An object of the route's `params`, `query`, `headers` and `body`. Each is
		 * the `schemaConverter` output in input mode.
		 * Models fill arguments from it, so describe fields, such as with `.describe()`.
		 */
		inputSchema: JsonSchema;
		/** The body schema of the route's only defined response. */
		outputSchema?: JsonSchema;
		/** `readOnlyHint` for `GET`, and `idempotentHint` for `PUT` and `DELETE`. */
		annotations?: ToolAnnotations;
	};
	/**
	 * Runs the route as a local call with the arguments the model sends, such as
	 * `{ query: { text: "hello" } }`, and resolves with an MCP `CallToolResult`.
	 */
	call: (
		args: Record<string, unknown>,
		options?: ToolCallOptions,
	) => Promise<ToolResult>;
	/** The route the tool calls, with its metadata. */
	route: RouteDefinition;
	/** The route's key path in the route tree, such as `["posts", "search"]`. */
	routePath: readonly string[];
};
```

## Serve over MCP

Register the tools on an SDK server. The SDK's `createMcpHandler()` creates a
server per request and serves it statelessly as a Fetch handler, next to the
app or in the framework's router. The SDK takes schemas as Standard Schemas, so
`fromJsonSchema()` wraps the definition's JSON Schemas. An input schema is an
object, so the arguments are typed as one:

```ts server.ts
import {
	createMcpHandler,
	fromJsonSchema,
	McpServer,
} from "@modelcontextprotocol/server";
import { createApp } from "@rest-rpc/server";
import { router } from "./router.ts";
import { tools } from "./tools.ts";

const mcp = createMcpHandler(() => {
	const server = new McpServer({ name: "blog", version: "1.0.0" });
	for (const { definition, call } of tools) {
		const { name, inputSchema, outputSchema, ...config } = definition;
		server.registerTool(
			name,
			{
				...config,
				inputSchema: fromJsonSchema<Record<string, unknown>>(inputSchema),
				...(outputSchema && { outputSchema: fromJsonSchema(outputSchema) }),
			},
			(args, { mcpReq }) => call(args, { signal: mcpReq.signal }),
		);
	}
	return server;
});

const app = createApp(router);

export default {
	fetch: (request: Request) =>
		new URL(request.url).pathname === "/mcp"
			? mcp.fetch(request)
			: app.fetch(request),
};
```

Protocol revisions before 2026-07-28 allow only an object as
`structuredContent` and `outputSchema`, so for their clients, leave out other
values.

## Use in an Agent Framework

An agent running in your own process doesn't need MCP. Map the tools to the
framework's tools, such as with the AI SDK:

```ts
import { jsonSchema, tool } from "ai";
import { tools } from "./tools.ts";

const agentTools = Object.fromEntries(
	tools.map(({ definition, call }) => [
		definition.name,
		tool({
			description: definition.description,
			inputSchema: jsonSchema<Record<string, unknown>>(definition.inputSchema),
			execute: async (args) => {
				const result = await call(args);
				if (result.isError) throw new Error(result.content[0]?.text);
				return result.structuredContent;
			},
		}),
	]),
);
```

## Choose Tools

`createToolsFromRoutes()` returns an array, so choose and change tools with
array methods. Each tool has its `route`, with its
[metadata](/docs/middleware#metadata), so tool options can be fields of your
metadata shape:

```ts
const agentTools = tools
	.filter(({ route }) => route.meta?.access !== "admin")
	.map((tool) => ({
		...tool,
		definition: {
			...tool.definition,
			description: tool.route.meta?.agentHint ?? tool.definition.description,
		},
	}));
```

## Merge Tools

A model receives the definition of every tool before it calls any, so a tool
for each route of a large API fills its context. `mergeTools()` merges tools
into two, whose definitions stay the same size however many tools there are:

- `findRoutes`, named `find_routes`, lists the name and description of each
  tool, filtered by words in `query`, and returns the definitions of the tools
  in `names`.
- `callRoute`, named `call_route`, calls a tool by name, with the arguments its
  definition describes.

```ts
const { findRoutes, callRoute } = mergeTools(tools);
const agentTools = [findRoutes, callRoute];
```

The merged tools are tools too, so they can be renamed or mapped like others.
Frequently used routes can stay tools of their own next to them:

```ts
const isFrequent = (tool: AgentTool) => tool.definition.name === "posts_search";
const { findRoutes, callRoute } = mergeTools(
	tools.filter((tool) => !isFrequent(tool)),
);

const agentTools = [...tools.filter(isFrequent), findRoutes, callRoute];
```

Tool names identify the merged tools, so two with the same name throw.

### Finding Routes

`find_routes` lists the tools whose name, title or description contains every
word of `query`, ignoring case. It finds routes by what they are named and
described as, so it works as well as the route tree's keys and the routes'
`.openAPI()` summaries describe them. It doesn't rank results or search
schemas and metadata.

For other search, such as by tags or with an index, write your own find tool
and use it with `callRoute`. A find tool returns the definitions the model
calls routes with:

```ts
const { callRoute } = mergeTools(tools);

const searchRoutes: AgentTool = {
	definition: {
		name: "search_routes",
		description: "Finds API routes by tag.",
		inputSchema: { type: "object", properties: { tag: { type: "string" } } },
	},
	call: async (args) => {
		const { tag } = args;
		const routes = tools
			.filter(({ route }) => route.openApi?.tags?.includes(String(tag)))
			.map(({ definition }) => definition);
		return {
			content: [{ type: "text", text: JSON.stringify({ routes }) }],
			structuredContent: { routes },
		};
	},
};

const agentTools = [searchRoutes, callRoute];
```

## Context and Headers

`call()` takes the [initial context](/docs/middleware#context) the routes
require, as `createApp()` does, and an abort `signal`. Headers the host
provides, such as the MCP request's `authorization`, are passed with `headers`,
which replace headers of the same name in the arguments:

```ts
const mcp = createMcpHandler(({ requestInfo }) => {
	const server = new McpServer({ name: "blog", version: "1.0.0" });
	for (const { definition, call } of tools) {
		server.registerTool(definition.name, config, (args) =>
			call(args, {
				context: { user: findUser(requestInfo) },
				headers: {
					authorization: requestInfo?.headers.get("authorization") ?? "",
				},
			}),
		);
	}
	return server;
});
```

## Results and Errors

`call()` resolves with an MCP `CallToolResult`, and doesn't reject. The result
is the response body. Its status, headers and cookies are left out, so a route
whose result an agent needs, such as the ID of a created post, should return it
in the body:

| Route outcome   | Result                                                       |
| --------------- | ------------------------------------------------------------ |
| A body          | The body as `structuredContent`, and as JSON text `content`  |
| A string body   | The string as `structuredContent`, and as it is in `content` |
| No body         | Empty `content`                                              |
| A `RouteError`  | `isError`, with the error as JSON text `content`             |
| Any other error | `isError`, with `INTERNAL_SERVER_ERROR` and no details       |

An error's JSON is the response an HTTP client receives, with its status and
whether the route defines it, so the model can act on it, such as fixing its
arguments after a request validation error:

```json
{
	"code": "POST_NOT_FOUND",
	"status": 404,
	"message": "Post not found.",
	"data": { "id": "2" },
	"defined": true
}
```

## Options

```ts
type CreateToolsFromRoutesOptions = {
	/**
	 * Converts Standard Schema definitions into JSON Schema.
	 * Without it, or when it returns `undefined`, a segment
	 * accepts any value.
	 */
	schemaConverter?: (
		schema: StandardSchemaV1,
		mode: "input" | "output",
	) => Record<string, unknown> | undefined;
	/**
	 * Called with each error a tool call returns, as the `RouteError` the model
	 * receives. An error that isn't a `RouteError` is sent as
	 * `INTERNAL_SERVER_ERROR`, with the thrown value as its `cause`, and the
	 * model receives none of it.
	 */
	onError?: (error: RouteError) => void;
};
```
