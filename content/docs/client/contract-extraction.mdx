---
title: Client Contract Extraction
description: Extract a minimal runtime contract from your server routes.
---

When you can't import your server code directly, such as for a browser bundle,
`extractContract()` gives the client a minimal runtime contract with the same types as your server routes.

:::tip[Using Contract-First?]
Import the [shared contract](/docs/contract-first) directly and skip this page.
:::

## Extract Routes with a Macro

Run it as a bundler macro so the bundle gets plain JSON:

```ts contract.ts
import { extractContract } from "@rest-rpc/core";
import { router } from "./router.ts";

export function getContract() {
	return extractContract(router);
}
```

```ts client.ts
import { createClient } from "@rest-rpc/core";
import { getContract } from "./contract.ts" with { type: "macro" };

export const client = createClient(getContract());
```

In a browser, the client calls the page's origin. Pass the
[client options](/docs/client/fetch-client#client-options) for an API on
another origin or under a mount path.

Bun supports macros natively. For Vite, esbuild, Rolldown, Rollup, webpack or
Rspack, use [`unplugin-macros`](https://github.com/unplugin/unplugin-macros):

```ts vite.config.ts
import Macros from "unplugin-macros/vite";
import { defineConfig } from "vite";

export default defineConfig({
	plugins: [Macros()],
});
```

`unplugin-macros` runs the macro in the runtime the bundler runs on, not through
the bundler, so the bundler's path aliases don't apply to the macro import or to
what `contract.ts` imports. Their imports follow the runtime's rules instead:
Node needs the extension on every relative import, as it does for server code,
while Bun also resolves imports without one. Importing `./contract.ts` works on
both, and type-checks with `allowImportingTsExtensions` in the client's
`tsconfig.json`.

## Extract Routes without a Macro

For bundlers without macro support (e.g. Turbopack), write the contract to
JSON in watch mode:

```ts scripts/extract-contract.ts
import { writeFile } from "node:fs/promises";
import { extractContract } from "@rest-rpc/core";
import { router } from "../router.ts";

await writeFile("contract.json", JSON.stringify(extractContract(router)));
```

```json package.json
{
	"scripts": {
		"contract": "node --watch scripts/extract-contract.ts",
		"dev": "npm run contract & next dev"
	}
}
```

```ts client.ts
import { contractFromJson, createClient } from "@rest-rpc/core";
import type { router } from "./router";
import json from "./contract.json";

export const client = createClient(contractFromJson<typeof router>(json), {
	origin: "http://localhost:3000",
});
```

A JSON import is typed by its values, or not at all, so `contractFromJson()`
types it as the route tree it was extracted from, and throws when the file
doesn't have the shape of an extracted contract. A macro returns the contract
with its type, so only this setup needs the type import of the router.

## What Extraction Runs

Both ways import `router.ts` at build time, and with it every module it
imports. Whatever those modules do when imported happens during the build too:

- A module that throws, such as one that validates environment variables,
  fails the build.
- A module that keeps the process alive, such as one that opens a database
  connection, starts a timer or listens on a port, keeps the macro or the
  script from finishing.
- Other side effects, such as writing log files, run in the build's working
  directory.

Keep these out of the modules routes import. Give handlers their services
through [context](/docs/middleware#values-from-the-host) that the server
creates, create them on first use, or share a [contract](/docs/contract-first)
that imports no server code.

## Limitations

The extracted contract has no schemas, so the client can't
[validate responses](/docs/client/fetch-client#response-validation), and
routes with [inferred responses](/docs/route-builder#return-responses) accept
any 2xx. If you need client-side validation, use a
[shared contract](/docs/contract-first).
