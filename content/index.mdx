<span data-home-page />

Define REST APIs with an expressive HTTP route builder and sensible defaults.
Call them through a typed client that feels like ordinary function calls.

`rest-rpc` puts HTTP first. Define routes alongside their handlers and infer
client types from their return values. Use your existing server framework,
middleware, and deployment model.

## Define Routes, Call Functions

<Tabs>
<Tab title="Routes">

```ts twoslash
// ---cut-start---
// @filename: server.ts
import { respond, route } from "@rest-rpc/server";
import { z } from "zod";

declare function createTodo(title: string): { id: string; title: string };
declare function findTodo(
	id: string,
): { id: string; title: string } | undefined;
// ---cut-end---
// POST /todos/create, JSON body, 200 result.
const create = route
	.body(z.object({ title: z.string() }))
	.handler(({ body: { title } }) => createTodo(title));

// GET /todos/:id with params, query, headers, an error, and response headers.
const get = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.query(z.object({ uppercase: z.enum(["yes", "no"]).optional() }))
	.headers(z.object({ "x-request-id": z.string().optional() }))
	.error("TODO_NOT_FOUND", { status: 404 })
	.handler(({ params, query, errors }) => {
		const todo = findTodo(params.id);
		if (!todo) throw errors.TODO_NOT_FOUND();
		const title =
			query.uppercase === "yes" ? todo.title.toUpperCase() : todo.title;
		return respond(
			{ ...todo, title },
			{ headers: { "x-powered-by": "rest-rpc" } },
		);
	});

export const routes = { todos: { create, get } };
```

	headers: { "x-request-id": "req_1" },
});

// @filename: client.tsx
import { api } from "./client-contract";
// ---cut-end---
import { createClient } from "@rest-rpc/core";
import { createTanstackQueryUtils } from "@rest-rpc/tanstack-query";
import { useQuery, useMutation } from "@tanstack/react-query";

const restrpc = createTanstackQueryUtils(
	createClient(api, { baseUrl: "http://localhost:3000" }),
);

const todo = useQuery(
	restrpc.todos.get.queryOptions({
		request: {
			params: { id: "todo_1" },
			query: { uppercase: "yes" },
		},
	}),
);
const create = useMutation(restrpc.todos.create.mutationOptions());

create.mutate({ body: { title: "Write docs" } });

:::tip[Small by design]
`rest-rpc` stays focused on the API boundary so it can fit into code you already
have. It types and validates what crosses the wire, and leaves routing features,
plugins, and server lifecycle to your stack. There is no built-in
authentication, caching, or dependency injection, and no framework adapters:
keep your framework's features, add a package, or build your own on
[middleware and context](/docs/middleware/). Adopt it one step
at a time, each useful without the next:

1. Define routes and infer request and response types for handlers you write.
2. Validate requests and responses at runtime.
3. Extract a contract and call the routes with the typed client.
4. Serve the routes with a one-line server, mount the catch-all handler, or
   register them on your framework's router.
   :::

## Common Questions

<Accordion>
	<AccordionItem title="Who is rest-rpc for?">
		`rest-rpc` is for developers who want end-to-end type safety and RPC-like
		ergonomics without replacing familiar HTTP concepts. You keep methods,
		paths, headers, bodies, status codes, and your existing framework, while
		route definitions connect server and client types.
	</AccordionItem>
	<AccordionItem title="Do I have to restructure my app?">
		No. Keep your framework, middleware, authentication, database access, and
		deployment model. Add typed routes at the API boundary and adopt the client,
		TanStack Query utils, or OpenAPI generation as they become useful.
	</AccordionItem>
	<AccordionItem title="Do I need a server framework?">
		No. If an app only needs typed, validated endpoints, serve them with a
		one-line server on Node HTTP, Bun, Deno, or Cloudflare Workers. If it needs
		a framework for other reasons, register the routes on the framework's router
		instead. Routes do not depend on how they are served, so you can change this
		later without changing them.
	</AccordionItem>
	<AccordionItem title="Do I need to learn a new API model?">
		The model is ordinary HTTP: methods, paths, request locations, status codes,
		headers, and response bodies. The route builder describes them directly,
		with sensible defaults for methods, paths, and success statuses.
	</AccordionItem>
	<AccordionItem title="Can I have a separate contract?">
		Yes. Define the HTTP interface independently, implement it with
		`@rest-rpc/server`, and share it directly with clients. See the
		[Contract-first Quickstart](/docs/contract-first-quickstart/).
	</AccordionItem>
	<AccordionItem title="What happens when something breaks?">
		You debug the same boundary you would debug by hand: method, path, query,
		headers, body, status, and response shape. Because those pieces live in one
		route definition, type errors and validation errors point back to that
		definition.
	</AccordionItem>
</Accordion>
